How to read this walkthrough
A clear model, with clear boundaries.
The interactive flowchart makes route conditions explicit. The walkthrough opens the artifacts and hand-offs for the selected route.
When a required definition does not exist
The current request cannot invent a KPI, relationship or permission. Clarify whether the user meant an existing approved definition. If the requirement is genuinely new, the accountable owners define its meaning, engineering verifies source mappings and calculations, independent review approves it, and controlled publication makes a version available for a later request. This page sends no review request and publishes no business definition.
What this page demonstrates
  • An English, step-by-step target request flow from question to answer.
  • A synthetic Ontario comparison: CAD 120 million to CAD 126 million, an increase of CAD 6 million (5%).
  • Eleven illustrative Registry records, explicit version references, a bound semantic plan and provider-specific query templates.
  • Fifteen predefined scenarios, including no-template recipe fallback, bounded planning, missing definitions, a disabled planner, rejected plans, stale responses and the original routes.
  • An interactive call-and-return diagram with request state, scenario-specific role participation and explicit deterministic controls.
  • A new synthetic bounded-planning example: product shares of CAD 126 million (49.2%, 34.1%, 16.7%).
The exact no-template branch presentation, share-of-total fixtures and scenario switches are teaching choices derived from the target contract. They are not a newly adopted production routing policy. Questions and outcomes are predefined; this page does not interpret arbitrary text.
No application source, deployed service, live model, provider connection or production acceptance has been verified by this simulation. It does not execute SQL, contact an LLM or connect to business data.
Important distinctions
Intent recognition, question-template matching, recipe selection and cache eligibility are separate decisions. A template miss is not a cache miss, and neither authorizes unrestricted SQL.

Controls preserved in the design
  • Authorize before protected metadata, data or model payloads; check current permissions again on follow-ups and reuse.
  • SQL uses the established App Service system-assigned managed identity direction. Databricks identity, connector and native grants require separate qualification.
  • Baseline SQL and Databricks support does not authorize cross-provider joins.
  • Early reuse uses pre-plan identities; post-plan reuse may use a semantic-plan identity. These are planned capabilities, not deployment claims. This demo skips its template-keyed early lookup when no question template matches; it does not claim every possible early cache requires a template.
  • Phase 2F.1 lifecycle classification is optional, trace-only observation. Existing authoritative recipe and access gates remain responsible for execution.
  • Audit, operational trace, usage and session memory have different purposes. Observable hand-offs are shown here, not hidden model reasoning.
